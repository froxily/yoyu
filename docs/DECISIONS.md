# Decisions

One line per decision: what was decided and why. Newest at the bottom.

## Made before the build

- Built as a PWA, not a native app: one codebase for Android and iPhone, live as soon as it deploys; can be wrapped as an Android app later with PWABuilder or Bubblewrap.
- The 28-hour limit is checked over every 7 consecutive days, not calendar weeks: that is how the rule is interpreted, and calendar weeks miss violations (test T3).
- Compliance is evaluated under two day attributions (split at midnight, and whole shift on its start day) and the worse result is reported: midnight-crossing shifts are common in part-time work and the rules don't say which attribution applies.
- Windows that mix regular and vacation days are reported as AMBIGUOUS between 28 h and 40 h: the rules don't clearly say which limit applies, so the app flags it instead of guessing.
- Capacity uses the strict 28 h limit for mixed windows, so following the app's "hours left" never produces an AMBIGUOUS result.
- Breaks are stored as a time interval, not a number of minutes: day splitting and late-night pay depend on when the break happened.
- Overlapping shifts are rejected by a PostgreSQL exclusion constraint: the database guarantees it even if application code has a bug.
- Time is integer minutes and money is integer yen; premiums use BigDecimal and round once per shift: avoids floating-point drift.
- All day logic uses Asia/Tokyo regardless of server or phone time zone: the rule applies to days in Japan.
- Past shifts are never blocked, only flagged: the app must reflect what actually happened.
- No residence-card or visa data is stored: the app only needs hours, and that data is sensitive.

## Made during the build

- Spring Boot 4.1.1 (current stable on start.spring.io) with its modular starters: matches the stack rule to use the current stable version.
- The Spring Security starter is added in Phase 3 together with its configuration: adding it earlier would put every endpoint behind a generated password.
- Flyway starts with an empty `V0__baseline.sql`: proves Flyway runs while keeping V1 exactly the spec's data model.
- Vite builds straight into `backend/src/main/resources/static` (git-ignored, emptied on each build), so no separate copy script is needed; files like `.well-known/assetlinks.json` go in `frontend/public`.
- Local datasource defaults (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`) match `docker-compose.yml`: they are non-secret local values, and production overrides them with environment variables.
- The JVM default zone is set to UTC in `main()`: one place, before Spring starts, and logs show UTC.
- Shift times must be whole minutes and the domain rejects seconds: durations are integer minutes, and rejecting is stricter than silently rounding.
- Invalid domain input (`Shift`, `VacationPeriod`, `JobRate`) throws `DomainValidationException`, so Phase 3 can map exactly that to 400; broken internal invariants (`Interval`, `Check`, a job with no rate) stay `IllegalArgumentException` and surface as 500.
- When both attributions give the same status, the reported one is the higher total, then CALENDAR_SPLIT: the higher total is the more severe reading, and a fixed order keeps results deterministic.
- A window's reported limit is the one that decides its status: a mixed window shows 2400 when it is a VIOLATION, otherwise 1680 (the limit that makes it AMBIGUOUS).
- `evaluate(from, to)` covers every window containing a date in the range and every vacation date in it; a draft is checked over the dates from its start to its last worked-or-break minute, which is a superset of what it can change.
- The domain finds the shifts a draft overlaps (touching is not overlapping); `/compliance/check` reports each one as an OVERLAP issue so the form warns before saving, and saving still returns 409 (service pre-check, database exclusion constraint as backstop).
- Pay for a date range includes shifts by start date (START_DAY), so one work day's overtime is never split across two ranges.
- `btree_gist` is available in PostgreSQL 16 (a trusted extension in the official image), so V1 keeps the spec's exclusion constraint and the service-side fallback is not needed.
- Entities hold `userId` and `jobId` as plain UUID columns instead of JPA associations: simpler, no lazy loading, and the database enforces the foreign keys.
- Entity ids are generated by Hibernate (random UUID) and `created_at` comes from the database clock (`source = DB`), matching the schema's `now()` defaults.
- JPA writes every mapped column, so job defaults (transport 0, colour `#3b82f6`) are applied in one place, `JobInput.withDefaults`, for both create and update; the SQL defaults only cover raw SQL.
- V2 adds a unique (id, user_id) on jobs and a composite foreign key from shifts (job_id, user_id), so the database rejects a shift that uses another user's job; the service still looks the job up by id and user id first and answers 404.
- Job lists are ordered by name: deterministic and easy to scan.
- All Spring integration tests use `@IntegrationTest`, so they share one context and one PostgreSQL container.
- V2 sets `shifts.updated_at` with a trigger using `clock_timestamp()` on every update, whatever the path (JPA or SQL) and even twice in one transaction; the entity reads the generated value back.
- Authentication is a server session (`SESSION` cookie, HttpOnly, SameSite=Lax); its Secure flag comes from `SESSION_COOKIE_SECURE`, which production must set to true.
- CSRF uses Spring Security's SPA setup (readable `XSRF-TOKEN` cookie, `X-XSRF-TOKEN` header); every response issues the cookie, and sign-in issues the rotated token in the same response, so the SPA never sends a request without one.
- Register, login and logout also require the CSRF token: prevents login CSRF.
- Register signs the user in: one round trip for the UI.
- Login gives the same 401 for an unknown email and a wrong password: no account enumeration at login.
- Passwords need at least 10 characters and at most 72 UTF-8 bytes (the BCrypt limit): longer passwords are rejected with 400 rather than silently truncated.
- The principal's username is the user id and the password hash is erased from the session: controllers get the id without a lookup.
- Creating (POST) or editing (PUT) a shift that has not ended yet and is not OK (AMBIGUOUS or VIOLATION) is rejected with 422 and its compliance result unless the request says `confirmed: true`; a shift that has ended is always saved and its violations returned. In-progress shifts count as future (stricter).
- `/compliance/check` requires a `jobId` of the user's own jobs, and `excludeShiftId` must be one of the user's shifts (404 otherwise): every lookup stays user-scoped.
- `/compliance` days use CALENDAR_SPLIT minutes; capacity covers today and the next 7 dates (8 entries), with today from the injected `Clock` in Asia/Tokyo.
- Date ranges (`from`, `to`, inclusive) cover at most 366 dates and return 400 otherwise: bounds the work per request.
- Responses give instants in ISO-8601 with the +09:00 offset; requests accept any offset but must include one.
- `DELETE /jobs/{id}` returns 204 whether it deleted or archived the job; the client re-lists. Shifts can still be added to an archived job (archiving only hides it from the default list).
- Unexpected exceptions return a 500 ProblemDetail ("Something went wrong.") and are logged server-side only; unique and exclusion violations are turned into 409 in the services, and any other database error is a 500.
- 401 and 403 from Spring Security go through the same `@RestControllerAdvice`, so every error is a ProblemDetail.
- API tests drive the real CSRF cookie and header instead of spring-security-test's `csrf()`, which swaps the token repository for the whole shared test context.
- Tests inject a mutable `Clock` set to 2027-06-01 by default, so test shifts are in the past unless a test moves the clock.
- A `/compliance` date with no worked minutes is OK; a worked date takes the worst of its own vacation-day check and every window containing it (replaces marking every date inside a non-OK window, which flagged days off): only worked dates can be fixed by changing a shift.
- A date counts as worked if either attribution gives it minutes (a shift that starts on it with a break until midnight still counts): stricter.
- Sessions are stored in PostgreSQL with Spring Session JDBC and expire after 30 days without use (`spring.session.timeout`): users stay signed in across browser, phone and server restarts and deploys. V3 creates Spring Session's PostgreSQL tables (lower-case names); Boot's own schema initializer is off so Flyway owns the schema.
- The session cookie has Max-Age equal to the session timeout, set when sign-in issues the session id and not refreshed per request: a sign-in lasts at most 30 days on a device, simpler than rewriting the cookie on every response.
- The session cookie settings (HttpOnly, SameSite=Lax, Secure, Max-Age) are applied in one `DefaultCookieSerializerCustomizer`: Boot maps `server.servlet.session.cookie.*` to Spring Session only on an embedded server, so MockMvc tests would otherwise see a different cookie than production.
- Deleting the account also deletes every session of that user (found by principal name): other devices are signed out at once and no row keeps the deleted user's id.
- The UI uses a small History API router (`router.ts`) and plain `fetch` instead of router or data-fetching libraries: nine flat routes, and every screen remounts on navigation, so nothing more is needed.
- Times are entered as Japan wall-clock date and times and sent as `YYYY-MM-DDTHH:mm:00+09:00`; instants are shown by adding 9 hours and reading UTC fields, so the device time zone is never used (Japan has no daylight saving time).
- In the shift form an end time at or before the start time means the next day, a break start before the shift start means the next day, and a break end at or before the break start is the day after the break start: one date field covers overnight shifts.
- Shift edit links carry the start date (`/shifts/{id}/edit?date=`) because the API has no single-shift GET; the form loads that date's shifts and finds the id.
- Home shows hours left today large and the 7 dates after today in the strip, and its banner lists issues for windows and days touching today through the next 27 days: those are the ones still current or ahead.
- History pages through 4 calendar weeks (Monday to Sunday, newest first, starting with next week), lists shifts under their start date and shows per-date calendar-split totals without weekly totals, since calendar weeks are not how the limit works (T3).
- The bottom navigation has Home, History, Add shift, Pay and Settings; Jobs and Long vacations open from Settings and from the onboarding steps, keeping five targets that fit at 360 px.
- After sign-in with no active jobs the app opens Jobs with a first-job step, then offers adding a shift or a vacation; Home and Add shift also point to Jobs while there are none.
- Every screen ends with a one-line disclaimer and Home and Settings show it in full: the product rule says the disclaimer is always shown.
- A shift saved with a non-OK result (a past shift, or a future one after "Save anyway") stays on the form showing its issues until the user taps Done, so a violation is never saved silently.
- Any 401 except a failed sign-in attempt clears the signed-in user and shows Login; a network failure shows "Offline — hours can't be checked right now".
- Jobs with shifts can't be deleted, so the job row's button is labelled Archive and its confirmation explains that a job without shifts is deleted instead.
- Local ports are 5728 for the Vite dev server (strict, so it never drifts to another port) and 8028 for Spring Boot instead of the defaults 5173 and 8080: other local projects, and service workers cached for their origins, used the default ports.
- Frontend logic that has no UI (form parsing, messages, time maths) is tested with Vitest in the Node environment, without a DOM library: the behaviour worth testing lives in plain functions, and screens stay thin.
- In the shift form an end time equal to the start time is rejected with "End must be after start", and a break end equal to its start with "Break end must be after break start" (replaces treating equal times as the next day, which turned 10:00–10:00 into a 24-hour shift); an earlier end time still means the next day.
- Every signed-in API request rewrites the session cookie with a fresh 30-day Max-Age, so a session lasts 30 days after its last use on both the server and the device (replaces setting Max-Age only at sign-in); health, sign-in, register and sign-out requests are skipped so they never write a second session cookie.
- Spring MVC's flash-map manager is replaced by a no-op and request-handled events are off (applied to MockMvc too): both read the session on every request, so `/api/health` would otherwise query the database and keep a scale-to-zero database awake; the SPA uses neither.
- Archived jobs are restored with `POST /api/jobs/{id}/restore` (200 with the job; restoring an active job changes nothing): restoring is an action, not a field edit, and keeps `PUT` for name, wage, transport and colour.
- A failed request shows "Offline — hours can't be checked right now" only when the browser reports it is offline; any other network failure, and any 502, 503 or 504 (whatever the body), shows "Can't reach the server — try again in a moment", and an error without details shows "Something went wrong." (replaces showing the offline text for every network failure and "Request failed (n)" for bodies that are not problem details): a sleeping or restarting server is not the user's connection.
- Home reloads its data when the app becomes visible again and remounts at midnight Japan time (a timer plus a check on every visibility change, since background timers are throttled): "hours left today" must never show yesterday.
- The service worker (vite-plugin-pwa 2, generateSW) precaches only the built app shell and static files, sends `/api/**` network-only and falls back to `index.html` only for navigations outside `/api/` and `/.well-known/`; it updates itself (`autoUpdate`).
- Placeholder icons are generated from `frontend/public/favicon.svg` with `@vite-pwa/assets-generator` (`npm run icons`) and committed, so builds don't need the generator; the maskable icon has a full teal background.
- Spring serves hashed files under `/assets/` with a one-year immutable cache and every other static file (`index.html`, `sw.js`, the manifest) with `no-cache`, so a deploy reaches installed apps on their next visit.
- Any GET for a path without a file extension outside `/api/` and `/.well-known/` that matches no file returns `index.html` (a `PathResourceResolver`), so deep links and refreshes work; missing files, unknown API paths and missing `.well-known` files stay 404.
- An offline banner shows "Offline — hours can't be checked right now" while the browser reports it is offline.
- Production runs on Azure App Service (Free F1, Linux, Java 21 SE, Japan East) as the executable jar with the built frontend inside, with a Neon free PostgreSQL in Singapore (Neon has no Tokyo region); nothing that costs money is created: only the F1 plan, no Application Insights or other add-ons.
- Spring honours `X-Forwarded-*` headers (`server.forward-headers-strategy=framework`): App Service terminates HTTPS at its front end, and HSTS and secure-request checks need the original scheme; no feature trusts the forwarded client address.
- The connection pool keeps no idle connections (`minimum-idle=0`, 30 s idle timeout, no keepalive) and Spring Session cleans expired sessions once a day at 04:00 UTC, so an idle app lets Neon scale to zero; `/api/health` uses neither the database nor the session (tested with Hibernate statistics and the session row).
- Neon is reached through its direct (non-pooled) host with `sslmode=require`: Flyway and session locking need session-level features that a transaction pooler does not keep.
- `docker compose up` builds the app image (multi-stage: Node build, Maven build without tests, JRE runtime as a non-root user) and runs it with PostgreSQL, so the whole app runs on a machine with only Docker; `docker compose up -d db` still starts only the database, and `DB_PORT` / `APP_PORT` move the host ports when 5432 or 8028 are taken.
- The Docker build and CI run `chmod +x mvnw` themselves rather than relying on the file mode stored in git.
- The product is called Yoyū (余裕, slug `yoyu`), a working name kept in one place, `frontend/src/brand.ts`, which the UI, page title and PWA manifest read (a guard test fails if the name appears anywhere else in the frontend); internal names (package `com.shift28`, Maven artifact, database, repository) stay Shift28: no user sees them and renaming them would touch every file and the Flyway history.
- Frontend tests have their own `tsconfig.test.json` with Node types, so `tsc -b` type-checks them without giving app code access to Node APIs.
- Limits are versioned in a `rule_versions` table keyed by `effective_from`, seeded by Flyway with today's rules under a sentinel date (2000-01-01) because no sourced start date exists; dates before the earliest version use it. New rules arrive only as a new migration: rules are part of the code's history, reviewed like code, with no admin surface to secure.
- A window that spans a rule change uses, for each limit, the strictest value in effect on any of its dates, and its issue carries `rulesChanged: true` and the versions involved; a version never changes results for earlier dates or windows that end before it, so past results are not rewritten.
- Rule versions are read from the table on each compliance check (one query on a table of a few rows): no cache to invalidate, and tests can add a version without restarting.
- The 40 h per 7 days during long vacations is kept although the ISA page only states 8 h per day: it comes from the Labour Standards Act 40-hour week, is stricter, and its source is now labelled as such.
- Every non-OK window and day lists its contributing shifts (id, job, start, minutes counted in that window or day) under its reported attribution, computed in the domain only for non-OK checks; job names are added by the service from the user's jobs, archived ones included.
- The shift being checked or saved is marked `draft: true` and has no id when new, because compliance is checked before the insert; the UI calls it "this shift".
- Exact-shape API assertions on issues were extended with the expected contributions rather than relaxed.
- `POST /jobs`, `/shifts` and `/vacations` take an optional `Idempotency-Key`: the key row is claimed with `INSERT … ON CONFLICT` in the same transaction as the write, so a concurrent duplicate waits on the primary key and then replays; the stored response is the exact JSON sent the first time. Reuse with a different request is 422 (as in the IETF Idempotency-Key draft); only 201 responses are stored, so failed requests roll the key back and can be retried; keys live 24 hours, expired keys are reclaimed on use and swept daily at 04:00 Japan time.
- A request's fingerprint is SHA-256 of method, path and the parsed request serialised with sorted properties: whitespace and field order don't matter, but equal instants written with different offsets count as different requests (stricter).
- The frontend keeps one key per form and reuses it only while the body is unchanged, so retrying after "Can't reach the server" cannot create a duplicate; a new key is made after a success.
- Deleting an account first deletes its idempotency keys, then the user, so every write locks the key row before the user row and never the reverse.
- Shifts, jobs and vacations have a JPA `@Version` column; `PUT` must send the version it loaded (400 if missing) and a mismatch is 409 with `"stale": true`, checked before the change and again by Hibernate at flush; `DELETE` and restore don't take a version (deleting or restoring is the same whatever was edited).
- Shift and vacation writes start by locking the user's row with `SELECT … FOR NO KEY UPDATE`, so each user's compliance check and save run one at a time; vacations are included because they change compliance too. `FOR NO KEY UPDATE`, not `FOR UPDATE`: inserting a key row takes a `KEY SHARE` lock on the user through its foreign key, and `FOR UPDATE` would make two concurrent creates with different keys deadlock (a test shows PostgreSQL detects that deadlock with `FOR UPDATE` and none with `FOR NO KEY UPDATE`).
- Lock order is always idempotency-key row, then user row.
- The notice reads "Informational only — not legal advice", followed by a link to the official ISA page and "If you hold an individual permission, your limits may differ." (replaces "planning aid, not legal advice"), with the same wording on every screen, in Settings, the README and the spec; the ISA page is the first source and the 40 h source is labelled as the Labour Standards Act week.
- The opening splash plays once per page load: its state lives in `App`, outside the route key, so SPA navigation and returning from the background never replay it; it unmounts when its own exit animation ends (a 2.5 s timer is the fallback), blocks taps while visible, is hidden from screen readers and stores nothing.
- The splash uses local font stacks (Yu Mincho / Noto Serif CJK for the kanji, the app's system font for the name) instead of the design's Google Fonts: no third-party requests and nothing more to cache offline.
- The manifest `background_color` is the splash teal `#0d7771` (replaces `#f4f5f7`) and an empty `#root` is painted the same teal, so Android's launch screen, the first paint and the splash match; `theme_color` and the icons are unchanged.
- Splash sizes use container-query units on a stage at most 28rem wide: identical to the 390 px design on phones without oversizing on desktop.
- Sign-up creates the account only after the emailed code is entered (pending name, username and password hash wait in `email_codes`): there is never an unverified account that can sign in.
- Email codes are 6 digits, stored as HMAC-SHA256 with `OTP_SECRET` (a plain hash of 6 digits can be brute-forced offline); a wrong attempt is counted in its own transaction so a rollback can't undo it, and a code is spent by deleting its row in the same transaction as the change it authorises, so it works once even under concurrent requests.
- Each code has a purpose (sign-up, confirm an existing email, password reset, change email, re-authentication) that is part of its HMAC and checked on use, so a code can't be replayed in another flow.
- Sign-up, forgot password and change email answer identically whether an address has an account, and mail is sent after commit on a background thread so timing doesn't tell either; the owner of a taken address gets a notice instead of a code, and unknown identifiers get no email at all.
- Login accepts an email (contains `@`) or a username; every failure is the same 401 and failures are counted per account, so switching between email and username shares one limit; unknown identifiers have their own bucket.
- Rate limits are an in-memory sliding window: enough for one F1 instance, lost on restart; scaling out would need a shared store.
- The client IP for rate limits is the socket peer unless `CLIENT_IP_HEADER` names a header the proxy overwrites (App Service sets `X-Client-IP`); client-supplied `X-Forwarded-For` is never trusted for this.
- Existing accounts keep their data; while mail is enabled an account whose email was never verified must enter a code at its next sign-in, and a failed send is a retryable 503, never a session. While mail is disabled they sign in as before so nobody is locked out.
- Google and LINE use Spring Security's `oauth2Login` with registrations built from environment variables (none configured, no OAuth endpoints); PKCE, state and nonce are on; LINE ID tokens are HS256 with the channel secret, Google's RS256 via its key set; no endpoint discovery at startup; provider access tokens are never stored.
- The OAuth callback never becomes the session principal: a custom success handler signs in the linked account (principal stays the user id), links an identity, records a re-authentication, or stores a pending sign-up, using a request-only security context. The request-only repository is set on `OAuth2LoginAuthenticationFilter` with an object post-processor, because `oauth2Login().securityContextRepository(...)` is overwritten by the app-wide session repository; tests drive the real callback with a stubbed token endpoint.
- Accounts are never merged by email: a Google identity whose verified email already has an account is sent to "sign in, then link in Settings"; LINE emails have no verified claim and are only suggested, needing a code before they become the account email.
- Linking requires a recent sign-in and a session intent created by a CSRF-protected POST; an identity already linked to another user is refused; one identity per provider per account.
- "Recent sign-in" means proof within 10 minutes: a password, a code to the verified email, or a provider sign-in with `auth_time` at most 5 minutes old and not LINE auto or SSO login (LINE is asked with `prompt=login` and `max_age=300`, Google for the `auth_time` claim); an ordinary social sign-in without fresh `auth_time` doesn't count.
- Wrong passwords in re-authentication and 403 `reauthenticate` / `verificationRequired` are not 401, so the app doesn't treat them as signed out.
- Password rules: 10 characters to 72 bytes, no composition rules, not the email or username, not in a bundled list of 9,111 common passwords (SecLists NCSC top 100k, MIT, entries of 10+ characters, compared case-insensitively). BCrypt stays at strength 10 (OWASP minimum) because F1 has a daily CPU quota.
- A password reset ends every session of the account and marks its email verified; accounts with only Google or LINE get a notice instead of a reset code.
- Changing the email locks the user row and checks the email hasn't changed since the code was sent; it ends the account's other sessions and notifies the old address. Unique indexes decide races, mapped to 409.
- Mail goes through a `MailService` interface (SMTP implementation) with 10 s connect, read and write timeouts and a single-thread queue of 50; `MAIL_ENABLED` turns every email feature on or off; production mail stays off until a real send is tested. Gmail SMTP with an app password is the free option because free transactional services need a domain.
- The product name in emails comes from one property (`mail.product-name`), the backend's only copy of it.
- Responses carry a Content-Security-Policy (`style-src` allows inline attributes only, for job colour dots), `Referrer-Policy: same-origin` and a restrictive `Permissions-Policy`.
- Local Compose adds Mailpit (bound to 127.0.0.1) for email; production never uses Compose, and the development `OTP_SECRET` exists only in the Compose file.
- Phone-number sign-in is not built: LINE notification messages need corporate approval and paid SMS is out of budget.
- Each user has a `session_version` (V8) that a password reset or email change increments; it is read together with the password hash at login and stored in the session principal, and every authenticated API request compares it with the database (one primary-key read), so a login that raced a reset can't keep a session alive. The check matches the decoded path, like Spring's routing, so an encoded path such as `/%61pi/...` can't skip it.
- Changes to a user lock its row first (`FOR NO KEY UPDATE`) and `users` updates write only changed columns (`@DynamicUpdate`), so a profile save can never write back an old password hash or email.
- An email code is checked in its own short transaction before the transaction that uses it starts (never nested), so parallel verifications can't hold two pool connections each; code endpoints are also limited to 60 requests per IP in 15 minutes.
- Sign-up always hashes the password, even when the email already has an account, so response time doesn't reveal which addresses are registered.
- Sign-in failures and forgot-password requests are limited per account and client IP (5 failures in 15 minutes, 3 requests an hour) under an account-wide ceiling from all clients (20 failures, 10 requests) (replaces 5 failures and 3 requests per account): one client that knows a username can no longer lock its owner out, locking needs several IPs, and the ceiling still bounds distributed guessing. A password reset clears the account's ceiling and the resetting client's count.
- A sign-in or re-authentication attempt is counted before the password is checked and refunded when it succeeds (replaces check, then record the failure, and replaces clearing the count after a successful sign-in): parallel guesses could otherwise all pass the check while BCrypt runs (12 parallel wrong passwords were all evaluated against a limit of 5), and a success refunds only its own attempt, so earlier failures from that client still count until they expire.
- Rate-limit buckets keyed by an account id are kept apart from the 10,000-key LRU, which holds only attacker-chosen keys (IPs, unknown identifiers, client pairs), so flooding it can't reset an account's counters; account buckets are bounded by the number of accounts and swept hourly.
- Google and LINE accounts can set a password (`PUT /api/account/password`, which also changes an existing one) after a recent sign-in instead of a separate old-password field: the re-authentication panel already offers the password, and accounts without one prove it with a fresh provider sign-in or a code to their verified email. A first password needs a confirmed email (the V7 check already requires an email) so it can be reset; LINE-only accounts add one first. Setting or changing it bumps `session_version`, ends the other sessions and emails a notice, like an email change.
- Completing a Google or LINE sign-up counts as a recent sign-in only when the provider sign-in was fresh (replaces always counting it): otherwise someone at a computer where the victim is still signed in to Google could create the victim's account and add a password to it.
- LINE re-authentication counts as recent when LINE omits `auth_time` only if the callback's own authorization request carried `prompt=login` (read from the request Spring removed at the callback, not inferred from the session), `amr` reports `pwd`, `lineqr` or `mfa` without `lineautologin` or `linesso`, and the ID token was issued within 5 minutes (replaces requiring `auth_time`, which LINE never sent: a real QR re-login returned `auth_time absent, amr [lineqr]`, leaving LINE-only accounts unable to add an email, set a password or delete). LINE documents that `prompt=login` disables auto login and that `amr` reports the method used; ordinary LINE sign-ins, consent alone, auto login and SSO still never count, and Google is unchanged. `max_age=300` is still sent in case LINE starts returning `auth_time`.
- A rejected provider re-authentication logs its evidence (`auth_time` and `iat` age, `amr`, whether the login was forced), never the subject, name or email: the only way to see what a provider actually sent.
- The remembered account action (kept in `sessionStorage` across a provider re-authentication) stores only its kind and provider or email, never a typed password; a password change resumes by reopening the form.
- Production runs in Azure's Malaysia West region (replaces Japan East): the Azure subscription used for this project limits the regions it may use (Japan East is not among them), and Malaysia West is a few milliseconds from Neon Singapore, which matters more than the hop from Japan because each request makes several database round trips. Yoyū has its own resource group, F1 plan, app and Neon project and shares nothing with the author's other projects.
- The F1 plan costs nothing, and the subscription has no payment method attached, so nothing can be billed.
- The server port comes from `PORT` (default 8028): App Service's built-in Java image tells the app which port to listen on through `PORT`.
- Production reaches Neon with `sslmode=verify-full&sslfactory=org.postgresql.ssl.DefaultJavaSSLFactory&channelBinding=require&socketTimeout=30` (replaces `sslmode=require`): pgjdbc's `require` encrypts without checking the certificate, while this checks the chain against the JVM truststore and the hostname, binds the SCRAM login to the TLS channel, and stops a hung read after 30 s instead of holding one of the five pooled connections forever.
- Yoyū's Neon project uses Postgres 16 like CI and local Docker, and Flyway runs at startup as the database's owner role.
- Behind App Service the client IP is the last value of `X-Client-IP` (the last value of the last header if there are several), used only if it is an IPv4 or IPv6 address; otherwise the socket peer (replaces taking the first value): probes through the real front end showed it appends the real address after whatever the client sent, as in `X-Client-IP: <forged>, <real>`, for forged, duplicate, malformed and empty headers.
- With `PUBLIC_ORIGIN` set (production):
  - every request is handled as that HTTPS origin, `Forwarded` and `X-Forwarded-*` are hidden from the application, relative redirects become absolute on the origin, and OAuth redirect URIs are built from it;
  - the session cookie is always Secure, whatever `SESSION_COOKIE_SECURE` says;
  - IPv6 client addresses are validated strictly without DNS (an address with a port is rejected);
  - the first fallback to the socket address is logged, because behind the proxy that fallback would put every client in one rate-limit bucket;
  - Boot's own forwarded-header handling is off (`server.forward-headers-strategy=none`, which also stops Boot from turning on Tomcat's RemoteIpValve when it detects Azure);
  - without it (local Docker, tests) Spring's ForwardedHeaderFilter applies as before.
  This replaces `server.forward-headers-strategy=framework` everywhere. App Service passes `Forwarded`, `X-Forwarded-Host`, `-Port` and `-Prefix` through unchanged, so a client could choose the host and scheme Spring saw. A fixed origin is safe because App Service only accepts HTTPS (it redirects HTTP and overwrites `X-Forwarded-Proto`) and routes by host.
- Google sends `auth_time` only for published, verified apps with "Session age claims" turned on (Google's security bundle). Until then:
  - a Google round trip can never prove a recent sign-in, and the callback reports `reauth-google-no-time` instead of the generic `reauth-not-fresh`;
  - Google-only accounts confirm with a code to their Google-verified email, so production needs mail before they can link, unlink, set a password, change their email or delete;
  - the accept rule itself is unchanged.
- The forced-login fallback (no `auth_time`, a `prompt=login` request, an interactive `amr` and a recent `iat`) applies only to LINE: it was justified by LINE's documentation, and no Google request is ever forced, so the rule now says so instead of relying on how requests are built.
- An emailed re-authentication code counts only while it was sent to the account's current verified email (replaces checking only purpose and user): a code still valid when the email changes must not prove the session.
- Sessions without an account last 10 minutes (`spring.session.timeout`) and signed-in sessions 30 days (`session.signed-in-timeout`, set at every sign-in), replacing 30 days for every session:
  - Every "Continue with Google/LINE" click by a visitor created a database row for 30 days. Ten minutes matches the OAuth intent, pending sign-up and email-code lifetimes, so a provider round trip still fits.
  - The session cookie keeps its 30-day Max-Age.
- An anonymous session is deleted once it is expired, idle for over 10 minutes, or 30 minutes old (by creation time), unless it holds a security context. Repeated requests refresh last access, so only an absolute age bounds how long an attacker can keep rows.
  - 30 minutes covers a provider round trip within the 10-minute idle window plus the 10-minute pending sign-up.
  - Expired sessions are deleted whatever they hold, because Spring Session already treats them as gone.
- Cleanup runs at startup and by a 10-minute sweep, and Spring Session's daily cron stays:
  - Startup re-arms the sweep from the newest surviving anonymous row.
  - Each new anonymous OAuth start keeps the sweep pending until a successful run after that session's 30-minute limit, so a failed run retries, and an idle app with nothing pending never wakes Neon.
  - Reason: F1 unloads idle apps, so a daily job alone may never run.
  - A row is normally gone within about 40 minutes (50 if a sweep fails), not counting downtime.
  - The cleanup uses the system clock because Spring Session stamps sessions with it.
- Starting Google or LINE sign-in is limited to 20 per client IP and 300 new sessions overall per 15 minutes. A blocked start redirects to `?error=rate-limited`.
  - The global cap counts only starts that would create a session, so signed-in users and sessions already in progress are never blocked by it.
  - Its counter can't be evicted by attacker-chosen keys. The per-IP counter is a fairness limit in the shared, evictable LRU.
  - Both are in memory per process and reset on restart, which an attacker can't trigger.
  - Worst case is about 900 anonymous rows (about 1.7 KB each) in one process lifetime.
- GitHub Actions signs in to Azure with OpenID Connect through a user-assigned managed identity whose federated credential accepts only this repository's `main` branch and whose only role is Website Contributor on the app (replaces the publish profile): a publish profile is a long-lived password and needs basic authentication turned on for the app's deployment endpoints, while OIDC tokens are short-lived and basic authentication stays off.
- Signed-out visitors at `/` see a landing page that describes the app, how sign-in data is used, and links to Create account, Sign in, the Privacy Policy and the Terms (replaces showing Sign in at `/`): Google requires an app homepage that describes the app and is not only a login page. A 401 for a user who was signed in still opens Login.
- `/privacy` and `/terms` are public routes that render before `/api/auth/me` answers (so a cold start or a failed boot request never hides them) and inside the app with its navigation for signed-in users; their text states only what the code and production configuration do, so any change to stored data, providers, scopes, logging, mail or retention updates them in the same change.
- The legal pages give `yoyu.notifications@gmail.com` (the address production mail is sent from) as the contact, kept in `brand.ts`, and describe the operator as an individual developer without a name: the user's choice.
- Email sign-up and the Google/LINE welcome step say that creating an account accepts the Terms and acknowledges the Privacy Policy; those two links open in a new tab so the form keeps its input.
- Google brand verification is not pursued on `yoyu.azurewebsites.net`: `azurewebsites.net` is on the Public Suffix List, so the host is its own top private domain, but without DNS access only a Search Console URL-prefix check is possible, a September 2026 report shows that did not satisfy brand verification for a host on the same kind of shared suffix, and F1 has no custom domains. Publishing needs no verification for `openid`, `email` and `profile`; Google then shows the app's domain instead of its name.
- Expired email codes are deleted at startup and by a 10-minute sweep that runs only while a sent or resent code may still be waiting to expire, re-armed at startup from the newest remaining code (replaces a daily 04:15 Japan-time job): F1 unloads idle apps, so a daily job may never run, and anonymous sign-up and password-reset requests create these rows (an unfinished sign-up holds a name, username, email and password hash). An idle app with nothing pending still never wakes Neon. Retry keys keep their daily job: only signed-in users create them, and deleting the account deletes them.
